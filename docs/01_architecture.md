# 01_architecture.md

## Назначение
Документ фиксирует архитектуру MVP-проекта «Цифровой двойник инвестиционных проектов Гатчины» на уровне технологий, модулей и взаимодействия частей системы.

Цель — иметь простую и понятную схему того:
- из чего состоит система;
- какие технологии используются;
- как части системы обмениваются информацией.

---

## Общая схема системы (MVP)

```
[Browser / Vue UI]
        |
        | HTTP (JSON)
        v
[Flask Calc Server]
        |
        |
[data/projects/]
  ├── gatchina-001/    <-- Папка проекта
  │     ├── project.json
  │     └── passport.pdf
  ├── gatchina-002/
  │     └── ...
  └── ...
```

- Frontend — тонкий клиент: UI, взаимодействие, отрисовка.
- Calc Server — единственный исполнитель бизнес-логики и всех расчётов.
- Storage (MVP) — файловая структура: отдельная папка на проект. Структура файлов не фиксируется сейчас.

---

## Основные части системы

### 1. Клиентское приложение (Frontend)
- Запускается в браузере.
- Отвечает за:
  - карту с маркерами проектов;
  - карточки проектов;
  - ввод параметров (инвестиционный калькулятор);
  - отображение KPI и графиков;
  - режим сравнения проектов.
- **Принцип:** Не содержит сложных финансовых формул и бизнес-логики расчетов.

**Стек технологий:**
- **Vue 3** (Composition API) — основной фреймворк.
- **Vite** — сборка проекта и локальный dev-сервер.
- **Pinia** — управление состоянием (фильтры, выбранные проекты).
- **Chart.js** — визуализация графиков.
- **Yandex.Maps JS API v3** — картография.

---

### 2. Сервер расчётов (Backend)
- Запускается локально (на этапе MVP).
- Отвечает за:
  - чтение данных из файловой системы;
  - выполнение финансовых расчётов (NPV, IRR, Payback Period);
  - применение пользовательских параметров к базовым сценариям;
  - возврат результатов расчёта в формате JSON.
- **Принцип:** Не знает ничего об интерфейсе и визуализации.

**Стек технологий:**
- **Python 3.10+**
- **Flask** — REST API.
- **NumPy / NumPy-Financial** — библиотека для точных финансовых вычислений и работы с массивами денежных потоков.

---

### 3. Хранилище данных проектов (MVP)
- Используется файловая структура (без базы данных).
- **Стратегия:** Один проект = Одна папка.

**Пример структуры:**
```
data/projects/
├── project-uuid-001/
│   ├── project.json       # Основные данные и параметры
│   ├── presentation.pptx  # Вложения
│   └── doc_scan.pdf
└── project-uuid-002/
    └── project.json
```

- Внутренняя структура `project.json` пока не зафиксирована (гибкая).
- Все изменения данных и кода фиксируются git-коммитами.

## Принципы архитектуры
1. **SSOT (Single Source of Truth) для расчетов:** Все финансовые расчёты выполняются строго на сервере (Python).
2. **"Тонкий" клиент:** Фронтенд занимается только отображением и сбором ввода.
3. **Чистый API:** Обмен между фронтом и сервером — только через JSON.
4. **Масштабируемость:** Архитектура локальная, но допускает перенос сервера в Docker/Cloud и замену файлового хранилища на PostgreSQL без переписывания фронтенда.
5. **Минимум зависимостей:** Используем только необходимые библиотеки.

---

## Взаимодействие компонентов
1. **Frontend** запрашивает список проектов (`GET /projects`).
2. **Backend** сканирует папки, собирает мета-данные и отдает список.
3. **Пользователь** открывает проект -> Frontend запрашивает детали (`GET /projects/<id>`).
4. **Пользователь** меняет параметры и нажимает "Рассчитать".
5. **Frontend** отправляет параметры на сервер (`POST /calculate`).
6. **Backend** прогоняет данные через формулы NumPy и возвращает результат.
7. **Frontend** обновляет графики и цифры.

---

## Что не фиксируется сейчас
- Точная структура полей `project.json` (зависит от финансистов).
- Конкретные формулы расчётов (будут реализованы отдельными функциями).
- Продакшен-инфраструктура (Nginx, Docker).
